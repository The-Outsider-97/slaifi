# Application Layer

The Application layer orchestrates SLAIFI's financial truth without redefining it. Domain and Engines remain the authority for financial concepts and calculations; Application decides which validated calculations participate in a use case and whether already-calculated evidence should be interpreted by SLAI.

## Dependency position

```text
API / future launcher
        ↓
Application use cases
        ├── Core
        ├── Domain
        ├── Engines
        └── Application-owned ports
                 ↑
          Integration adapters
```

Application code must not import concrete infrastructure or SLAI runtime modules. Integrations may implement Application-owned contracts, but the dependency is inverted toward the Application contract.

## Implemented use cases

- `AnalyzeMarketSeries`: validates a chronological, single-asset OHLCV series; composes Features, Technical and Risk calculations; optionally requests contextual SLAI interpretation.
- `AnalyzePortfolio`: composes portfolio valuation, risk metrics and goal feasibility from supplied domain data; optionally requests contextual SLAI interpretation.
- `EvaluateFinancialGoal`: performs deterministic target arithmetic independently of portfolio analysis and can optionally ask SLAI to explain the already-calculated feasibility result.
- `GetMarketOverview`: retained from the architecture-foundation vertical slice.

`evaluate_goal_bundle()` is the single Application-level composition point for deterministic goal arithmetic used by both `AnalyzePortfolio` and `EvaluateFinancialGoal`; the formulas themselves remain in `engines/goals`.

## Evidence model

Application reasoning requests separate:

1. authoritative observations and Engine results;
2. hard constraints;
3. explicit assumptions;
4. uncertainty metadata;
5. the qualitative reasoning objective.

SLAI output is attached as a separate `ReasoningResult`. It is never written back into Engine output or used to overwrite portfolio, risk, feature or goal calculations.

## Trace semantics

`request_id` is caller/API trace metadata. It may originate from `X-Request-ID` and is useful for end-to-end diagnostics. `correlation_id` belongs to an individual SLAI reasoning operation and is generated by the SLAI adapter unless an internal caller deliberately supplies one. Business identifiers such as `portfolio_id` are not used as reasoning correlation IDs.

This distinction prevents repeated analysis of the same portfolio or asset from overwriting SharedMemory reasoning envelopes.

## Non-responsibilities

Application does not fetch external market data inside analytical use cases, persist portfolios, perform HTTP serialization, instantiate SLAI agents directly, generate brokerage orders or redefine financial formulas.
